# Observability reports

The operational view of the Cost and Latency pillars (see [OBSERVABILITY.md](../OBSERVABILITY.md)). Two scripts, two nightly crons, two report families — all built off the same Langfuse trace data.

- [`scripts/cost_report.py`](../../scripts/cost_report.py) attributes token usage to a *task type* (`cache-hit` vs `rag-full`) and a *pipeline stage* (`embedding`, `rerank`, `llm`, …), priced against [`scripts/pricing.py`](../../scripts/pricing.py).
- [`scripts/latency_report.py`](../../scripts/latency_report.py) attributes per-trace and per-stage latency (p50 / p95 / p99) to the same task types and stages. Same classifiers; symmetric reports.

## Files

| File | Source | When it updates |
|---|---|---|
| [`cost_sample.md`](cost_sample.md) | `tests/fixtures/observations.json` | Whenever the fixture changes — checked in, regenerated by hand. |
| `cost_<YYYY-MM-DD>.md` | Live Langfuse Cloud | **Auto-generated and committed every day at 06:00 UTC** by [`cost-report-nightly.yml`](../../.github/workflows/cost-report-nightly.yml). Also triggerable on demand. |
| [`latency_sample.md`](latency_sample.md) | `tests/fixtures/observations_latency.json` | Whenever the fixture changes — checked in, regenerated by hand. |
| `latency_<YYYY-MM-DD>.md` | Live Langfuse Cloud | **Auto-generated and committed every day at 06:30 UTC** by [`latency-report-nightly.yml`](../../.github/workflows/latency-report-nightly.yml). Also triggerable on demand. |

## Regenerating

### From the checked-in fixtures (no Langfuse needed)

```bash
python -m scripts.cost_report --source file \
  --input tests/fixtures/observations.json \
  --output docs/reports/cost_sample.md

python -m scripts.latency_report --source file \
  --input tests/fixtures/observations_latency.json \
  --output docs/reports/latency_sample.md
```

### Automated (nightly, what runs in production)

Both crons live in [`.github/workflows/`](../../.github/workflows/). They run on offset schedules (06:00 and 06:30 UTC) so they don't compete for the runner, pull the last 7 days of traces from Langfuse Cloud, write the dated report, and commit it back to `main` with `[skip ci]` (so the main CI doesn't re-trigger on the bot commit).

One-time setup (already configured):

- Three GitHub repository secrets: `LANGFUSE_HOST`, `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY`.
- A fine-grained PAT in `BOT_PAT` (Contents:write on this repo only) so the bot push clears branch protection on `main`.

You can also trigger either workflow manually from the GitHub Actions tab → *Run workflow*.

### Manual / local

Requires `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY`, and `LANGFUSE_HOST` set in your environment or `.env`:

```bash
python -m scripts.cost_report --source live --days 7 \
  --output docs/reports/cost_$(date +%Y-%m-%d).md

python -m scripts.latency_report --source live --days 7 \
  --output docs/reports/latency_$(date +%Y-%m-%d).md
```

If the Langfuse SDK shape ever drifts, the only thing to patch is `fetch_from_langfuse()` in each script — the aggregation logic is insulated from it.

> **Self-hosted vs Cloud.** Both scripts deliberately use only **v1 API endpoints** (`trace.list`, `trace.get`). The newer v2 `observations.get_many` is Cloud-only — calling it against self-hosted Langfuse returns 404 with `"v2 APIs are currently in beta and only available on Langfuse Cloud"`. The v1 approach (`trace.get` returning observations inline) works on both deployments at the cost of one extra HTTP round-trip per trace.

## How to read a cost report

1. **What does an answer cost on average?** → *Cost per successful task* row in *Aggregate*.
2. **Is the cache earning its keep?** → Compare `$/task` for `cache-hit` vs `rag-full` in *By task type*. Cache hits should be 2–3 orders of magnitude cheaper.
3. **Where would I save the most by optimizing?** → `Share` column in *By pipeline stage*.
4. **Are any models unpriced?** → If a span's model is missing from [`scripts/pricing.py`](../../scripts/pricing.py), it shows up with `$0.000000` but real token counts. Update the pricing table.

## How to read a latency report

1. **How long does a request take at the tail?** → *p95* and *p99* rows in *Aggregate*. Mean hides the tail; percentiles don't.
2. **Is the cache earning its keep on latency too?** → Compare `p95` for `cache-hit` vs `rag-full` in *By task type*. Cache hits should be 100×+ faster.
3. **Where is the time going?** → *Share of time* column in *By pipeline stage*. Whatever's at the top is where latency reduction pays back the most — typically the LLM stage.
4. **What are the outliers?** → *Slowest traces (top 10)* — concrete trace IDs to inspect in Langfuse when defining SLOs or chasing a regression.
